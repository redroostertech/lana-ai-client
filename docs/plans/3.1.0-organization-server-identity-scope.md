# Organization and server identity binding for 3.1.0

**Status:** Scoped proposal; implementation not started  
**Last updated:** 2026-10-26  
**Target:** 3.1.0 release initiative, with coordinated client, Core API, and hosted discovery changes  
**Applies to:** `lana-ai-client`, `LANA-AI`, and `RedRoosterTech-Web`

Selecting an organization must establish which deployment the client will authenticate to. Today, the client can resolve one hosted organization, replace its server URL with a development override, and retain the original organization's identity and service metadata. A healthy response from the replacement server is sufficient to continue to login.

The proposed release requirement is to bind the selected organization, verified deployment, local tenant, and authenticated session before enabling normal application use. Preserve local development through an explicit local connection mode that uses the local server's identity and does not borrow a hosted organization's configuration.

The user requested the 3.1.0 target. The inspected desktop source reports version 4.1.0, while the local API package reports 3.0.0. Release coordination must identify the corresponding desktop version; this scope does not propose downgrading the client or changing version numbers.

## Observed behavior and evidence

On 2026-10-26, the user reported that both `redrooster` and `mwestbrooks` could be selected while pointing the development client at `http://127.0.0.1:8080`. A read-only lookup of `organizations_production` confirmed both hosted records are active, with domains `redrooster.lanaai.io` and `mwestbrooks.lanaai.io`. The local discovery endpoint identifies a different namespace: the PostgreSQL UUID of **Westbrooks Personal**.

The code establishes the following path:

1. [Hosted discovery](../../../RedRoosterTech-Web/routes/lana-ai.js), `POST /v1/discovery`, requires a matching hosted `org_id` and `domain`, with `status: active` and `is_active: true`.
2. [The login page](../../src/login.html), `resolveOrganization`, retains the hosted identity, tier, enabled apps, and Burst/Forge configuration. The submit handler then replaces only the network destination when the development override is visible and populated.
3. The page's `verifyServer` accepts `status: healthy` from `/api/health/discovery`. It does not compare the destination's identity with the selected organization.
4. [The API client](../../src/js/api.js), `login`, submits email, password, and optional MFA to that destination. It stores the returned token and user without comparing them with the selected hosted identity.
5. [Electron startup](../../electron-main.js) checks reachability and refreshes hosted metadata concurrently. [Electron discovery](../../electron-discovery.js) accepts any server with an organization ID; startup uses that result as a truthy reachability check rather than comparing identities. Its metadata merge preserves the saved URL.
6. [Connection storage](../../electron-storage.js) persists the resulting mixture of hosted identity, server URL, and service configuration for subsequent launches.

Existing backend controls still matter. [Login](../../../LANA-AI/src/services/processor/routes/auth.routes.js) verifies the password and applicable MFA and signs a JWT with the user's database organization. [Authentication middleware](../../../LANA-AI/src/shared/middleware/auth.middleware.js) verifies the token, checks a session, loads the user, and checks token/user organization consistency. The reported behavior demonstrates an identity-binding gap; it does not establish that an unauthenticated user can read another organization's records. Cross-organization authorization and credential-exposure impact need targeted verification.

The [local health repository](../../../LANA-AI/src/services/processor/health/health.repository.js), `getDiscoveryOrganization`, currently returns the oldest active organization row. That informational lookup is not an authoritative deployment identity and must not become the security check unchanged.

## Risk and release priority

Treat identity binding as a proposed 3.1.0 security release gate. Assign final severity after testing the affected authorization and service-credential paths.

| Risk | Current evidence and practical consequence |
| --- | --- |
| Misleading organization context | Hosted organization A can remain displayed while login and data access occur on server B. A user could enter or upload information to the wrong deployment. |
| Credential delivery to an unintended server | The override changes the destination of password and MFA submission. A health response alone cannot establish that a server is trusted to receive them. Credential theft was not exercised. |
| Mixed service configuration | Discovery can return Burst/Forge keys, service URLs, tier, and enabled apps, and the client retains these across the override. The route supports returning keys when populated; whether usable credentials are exposed or accepted across organizations requires a separate focused check. |
| Persistent mismatch | Saved connection and startup refresh paths can preserve the wrong identity/URL pairing after the initial login. |
| Incomplete development gating | [Frontend config](../../src/js/config.js) currently sets `DEVELOPMENT_MODE: true`. Electron reports development from `NODE_ENV`, and the inspected [build script](../../scripts/build-client.sh) resets debug mode without resetting that flag. Packaged release behavior needs artifact-level verification; hiding a field is insufficient enforcement. |

No passwords, connection strings, service keys, or session tokens belong in this scope or its future test evidence.

## Identity contract

Use distinct fields for distinct identities. Do not compare a hosted slug directly with a PostgreSQL UUID or infer equivalence from matching names, domains, or healthy endpoints.

| Concept | Authority and proposed use |
| --- | --- |
| Hosted organization ID | Control-plane identifier such as `mwestbrooks`; resolved by hosted discovery. |
| Deployment ID | Stable registered deployment identity; survives ordinary address changes and identifies the authorized server. |
| Local tenant ID | PostgreSQL `organizations.id`; governs users, sessions, queries, and stored data. |
| Verified endpoint | Origin authorized for that deployment, including an explicitly approved LAN/VPN route. |
| Session identity | Authenticated user and local tenant, bound to the deployment and token issuer/audience. |

The trusted mapping is **hosted organization → deployment → local tenant**. Provisioning or an authenticated administrative registration establishes it; a client cannot create or rewrite the mapping by submitting an organization ID. Reuse the existing [deployment identity repository](../../../LANA-AI/src/services/processor/provisioning/deployment-identity.repository.js) and [schema](../../../LANA-AI/src/migrations/20260616_deployment_identity.sql), which already distinguish the control-plane slug and deployment ID from a box-local UUID and store an identity public key. Inspect the bootstrap and rebind lifecycle before extending the contract.

For registered deployments, require a trusted discovery binding and proof that the contacted server owns the registered deployment identity. A candidate design is a bounded-lifetime control-plane statement plus a fresh server challenge signed by its registered identity key. Bind the proof to the expected deployment, endpoint policy, and challenge; reject expiration, replay, invalid signatures, and revocation. A copied JSON organization ID or self-signed claim is not sufficient. Final wire format, trust-root distribution, rotation, and revocation policy are design decisions to settle before implementation.

## Required behavior

### Hosted and registered deployments

- Resolve the hosted organization and its registered deployment over an authenticated transport. Obtain only public connection metadata before login.
- Verify the actual server's identity before sending passwords, MFA codes, bearer tokens, session refresh requests, or background service requests. Validate redirects and endpoint changes; a redirect must not carry credentials to a different unverified origin.
- Require the authenticated session's local tenant and deployment to match the trusted mapping before persisting or using the session. A client-provided expected identity is a constraint to validate, never an authorization grant.
- Keep authorization in Core. Preserve user/session organization checks and verify equivalent enforcement on login, refresh, `/me`, and protected routes, including handlers that perform their own JWT validation.
- Reject a mismatch with a clear connection error and a return to organization selection. Do not offer “continue anyway,” silently relabel the organization, or substitute whichever active database row is found first.
- Apply the same validation to initial connection, saved connection resume, background refresh, server switching, deep links, and reconnect after endpoint changes. Main-process IPC must enforce the binding independently of renderer fields.
- Keep service configuration, capabilities, and cached data scoped to the verified deployment/tenant. On a switch or mismatch, stop background requests and discard or quarantine connection-specific tokens and service credentials. Preserve user documents and unrelated local data.

### Explicit local development

Provide a separate local-development connection path in an unpackaged development build. It connects to the local API, authenticates against its users, and displays the actual local organization with a persistent development indicator. It does not require selecting `redrooster` or any other hosted organization to unlock local login.

Default this mode to a validated loopback endpoint. Remote development needs an explicit trusted-deployment policy, not an unrestricted URL bypass. The local mode must not import production Burst/Forge credentials, entitlements, or hosted organization branding. Any cloud-service testing needs separately authorized development credentials.

Packaged production builds must reject development override configuration in the main process even if `NODE_ENV`, renderer config, local storage, or IPC input is manipulated. Test the built artifacts rather than relying only on source flags. This mode does not waive backend authentication, tenant checks, or MFA.

### Discovery credentials and entitlements

The current discovery route's Burst/Forge fields require investigation within this release scope. Determine whether populated credentials are returned without authenticated organization membership and what their recipients permit. Do not test by spending credits or invoking another organization's services.

The target contract keeps public discovery secret-free. Obtain service credentials only after validating membership and deployment identity, with appropriate scope, audience, and lifetime. Prefer backend-mediated access when an existing service supports it. Backend services must enforce entitlement and organization ownership; client tiles and discovery metadata are presentation, not authorization. Confirmed exposed credentials require a separate inventory and coordinated rotation/remediation plan.

This work belongs to Core authentication/provisioning and the client shell. It does not introduce a shared multi-tenant runtime, alter the Pip.cpp model configuration, redesign the login page beyond connection modes/errors, or replace password/MFA authentication.

## Acceptance tests

Use isolated organizations A and B with separate users, tenants, deployment identities, and signing material. Include successful controls alongside every rejection case.

| Scenario | Required outcome |
| --- | --- |
| A resolves to its registered server and A's user authenticates | Login succeeds; displayed organization, stored connection, session tenant, and service configuration agree. |
| Select A and point at B, including a healthy B | Rejected before any password, MFA, token, or refresh request reaches B; no mixed connection is saved. |
| B copies A's public ID or replays a proof | Proof validation fails. Also reject wrong key, audience, endpoint binding, expired proof, and revoked deployment. |
| Valid deployment with a wrong-tenant user or token | Authentication/protected access fails server-side. Exercise login, `/me`, refresh, middleware, and a real scoped data route. |
| Hosted slug differs from the correct local UUID | The registered mapping succeeds. Raw string equality is not used as identity binding. |
| Old saved connection contains A metadata and B URL | Upgrade/relaunch refuses automatic resume and requests verified reconnection; no old token or service key is sent to B. |
| Background discovery changes identity or endpoint | The client revalidates before adopting metadata or making authenticated requests. A mismatch is not treated as temporary discovery unavailability. |
| Discovery is unavailable | An already verified connection may continue only within the defined validity/revocation policy. New or unverified connections cannot establish trust from health alone. |
| Explicit local development | The local user logs in to the actual local tenant without hosted organization selection or production service credentials. Wrong local credentials still fail. |
| Packaged build with development flags, tampered saved state, or direct IPC | The override is rejected and identity checks still run. Cover supported desktop platforms. |
| Redirect, URL alias, or LAN/VPN route change | Credentials remain withheld until the destination is verified under its registered endpoint policy. |
| Unauthenticated discovery | Only public metadata is returned; no reusable Burst/Forge credential. Post-login service access requires the correct membership/deployment. |

Record network destinations and whether sensitive fields were transmitted, without recording their values. Run the impacted client tests, Core auth/integration tests, hosted discovery contract tests, and a packaged-client login scenario against the candidate commits. Reproduce the mismatch with the fix disabled and confirm the regression test fails for the expected reason.

## Rollout and decisions before implementation

1. Confirm the 3.1.0 product release and corresponding desktop release version, and assign an owner for each work package.
2. Inventory active registered deployments and local-only installations. Define the migration from existing provisioning records to the explicit local-tenant mapping; do not infer it from the first active row.
3. Agree on proof format, endpoint policy, key distribution/rotation, revocation freshness, and bounded offline behavior. An unsigned equality check is not a substitute for this decision.
4. Ship additive server/control-plane capabilities and registration tooling, then the client enforcement and connection migration. Missing or mismatched identity must not trigger a legacy bypass. Explicitly decide the minimum supported client/server combination.
5. Mark old saved connections unverified and revalidate before reuse. Explain reconnection clearly; do not delete business data. Verified existing connections and new connections need separate offline rules.
6. Review the public discovery credential findings before release. If exposure is confirmed, coordinate credential changes without publishing secrets or breaking clients silently.
7. Release only after the acceptance matrix passes and mixed-version, rebind, and rollback exercises preserve the identity checks. Rollback must not restore the vulnerable override behavior.
